# API

The contract between the backend ([grigri_api/](../grigri_api)) and the
app. Architecture, data model and environments: [backend.md](backend.md).

All data comes from the backend. GA (prod) holds real people's data plus
the demo showcase (fictional climbers and their plans, marked `demo`); RC
and local also get made-up test data from a seed (never in GA). Real
plans' requests wait for real members everywhere; a demo plan's group says
yes at once.
An admin can list everyone and block or unblock them ([admin.md](admin.md)),
and answer reports; anyone can report content and block someone for
themselves, and the API filters objectionable words
([moderation.md](moderation.md)).

## Architecture (cost first: $0 idle)

- One TypeScript Lambda (Node.js 22, arm64, 256 MB) with an internal router,
  behind one API Gateway **HTTP API** ($1/M requests), served under `/api/*`
  by the site's existing CloudFront distribution (same origin as the web
  app, so no CORS in prod), and only through it: a request that skips it
  gets 403 ([origin check](origin-check.md)).
- One DynamoDB table, on-demand (PAY_PER_REQUEST), single-table design,
  point-in-time recovery on in prod only.
- Photos, and the chat's photos and videos, in S3 (private), uploaded with
  presigned POSTs, served by the same CloudFront under `/photos/*` (origin
  access control). Never in DynamoDB (400 KB item limit).
- GriGri Pics, Grigri's own crag photos, in a bucket of their own, served
  under `/pics/*`; the API reads only their catalog ([pics.md](pics.md)).
- Auth: the API's own **sessions** (see [Sessions](#sessions)). The app
  trades a Google ID token (or, on iOS, an Apple identity token) for a
  session token once (`POST /api/session`, where the function verifies
  the token), then sends
  `Authorization: Bearer <session token>` on every call. A session lasts
  until sign-out, or 365 days without use. The HTTP API has no
  authorizer: the function authenticates every request (one DynamoDB
  read).
- Live updates: after a change the function publishes a hint to each
  affected climber's MQTT topic on AWS IoT Core; the app subscribes with
  its session token through an IoT custom authorizer (see
  [Live updates](#live-updates) and [live-updates.md](live-updates.md)).
- Stacks per stage: `<prefix>-api` (prefix `grigri` for prod, `grigri-rc`
  for RC), next to the existing `<prefix>-web`.
- Local: the same CloudFormation template (`grigri_api/template.yaml`) deployed into Floci (Lambda, HTTP API,
  DynamoDB, S3), like prodbytes/presence's `presence_floci/init/ready.d/05-auth-api.sh`,
  and Floci's CloudFront routes `/api/*` and `/photos/*` to it.
- **Dev mode, local only**: when no Google web client ID is configured
  locally, the API takes the caller from an `X-Grigri-Dev-User: <email>`
  header, and `POST /api/session` also takes `{"devUser": "<email>"}`
  (a real session for `dev#<email>`). The template must refuse dev mode
  unless the stage is `local` (a CloudFormation Rule), so it can never be
  deployed to RC or GA; the function also ignores the header and refuses
  `devUser` unless its stage is `local`.

## Identity

- A signed-in Google account is a **subject** `https://accounts.google.com#<sub>`
  (whichever issuer spelling the token had), an Apple ID `apple#<sub>`
  (`dev#<email>` in dev mode), linked to one
  **climber id** (random, URL-safe, generated by the server at the first
  profile save). Emails are never returned to anyone; the API keeps each
  climber's verified email privately, to ask rbacr about their roles.
- **Every role is rbacr's** ([roles.md](roles.md)): `admin`, `premium`
  (granted while paid by the Stripe webhook, or the App Store's signed
  transactions and notifications; admins hold it through
  rbacr's implication) and `blocked` (`premium-rc` and `blocked-rc` on
  the RC).
- **Admin**: decided by [rbacr](roles.md) on every request: the
  session's verified email (`email_verified` true when the session was
  made) holds the `admin` role of rbacr's `grigri` system (rbacr's roots
  hold every role, so they're admins too). The API asks
  `POST <RbacrUrl>/api/check` `{email, systemId: "grigri", role: "admin"}`
  with an rbacr root's API token (template parameter `RbacrToken`, from
  the repository secret `GRIGRI_RBACR_TOKEN`), with a 2 s timeout, and
  keeps each answer for 60 s per Lambda instance, so a granted or revoked
  role shows within a minute. It fails closed: no token, an error or a
  timeout means not an admin (and isn't kept); rbacr not knowing the
  `grigri` system or its `admin` role means nobody is. Both stages ask
  production's rbacr (https://rbacr.nu01.com). Locally the API asks the
  local rbacr with `.env`'s `RBACR_TOKEN`, and in dev mode the header's
  (or `devUser`'s) email counts as verified.
- **Roles**: `GET /api/me` also gives my [roles](roles.md), with the same
  token: `POST <RbacrUrl>/api/roles` `{email}` (my verified email), my
  effective roles in the `grigri` system plus my global ones (`root`),
  sorted, without duplicates; kept 60 s per Lambda instance like the
  admin answer. No token, an error or a timeout (2 s) gives `null`, never
  kept. Without a verified email, `null` too.
- **Blocked**: a climber an admin blocked ([admin.md](admin.md)) gets
  403 `{"error": "blocked"}` from every route but signing out.

## Sessions

Google ID tokens expire after an hour and can't be refreshed quietly on
the web, so the API issues its own sessions:

- `POST /api/session` (public; the only route that takes an ID token),
  body `{"idToken": "<Google ID token>"}`, or for Sign in with Apple
  `{"appleIdToken": "<Apple identity token>", "nonce": "<raw nonce>",
  "authorizationCode"?: "<Apple's code>", "name"?: "<given and family
  name>"}` (see [Apple](#sign-in-with-apple) below). The function verifies
  it: RS256 signature against Google's keys
  (`https://www.googleapis.com/oauth2/v3/certs`, cached across warm
  invocations), `iss` `accounts.google.com` or
  `https://accounts.google.com`, `aud` the Google **web** client ID or
  one of the stage's **iOS** client IDs (template parameter
  `GoogleIosClientIds`: production's `GOOGLE_IOS_CLIENT_ID`; the RC's
  `GOOGLE_IOS_CLIENT_ID_RC` and production's, while phone builds for the
  RC keep production's bundle ID), not expired; with no web client
  configured, none. It keeps the token's `name` claim (whitespace collapsed, at
  most 60 characters) for the profile `GET /api/me` creates; dev mode
  uses the email's part before the @. → `{"token": "<opaque>", "expiresAt": "<ISO time>"}`. 401
  `{"error": "invalid Google ID token"}` for a bad, expired or foreign
  token; 400 without `idToken` (or `appleIdToken`). Dev mode only: `{"devUser": "<email>"}`
  instead (401 outside dev mode).
- <a id="sign-in-with-apple"></a>**Sign in with Apple** (every platform,
  [sign-in.md](sign-in.md#token-checks)): the function verifies
  `appleIdToken`: RS256 signature against Apple's keys
  (`https://appleid.apple.com/auth/keys`, cached across warm
  invocations), `iss` `https://appleid.apple.com`, `aud` the app's
  bundle ID (template parameter `AppleBundleId`, default
  `com.nu01.grigri`: Apple's sheet on iOS) or the Services ID
  (`AppleServiceId`, default `com.nu01.grigri.signin`: Apple's web flow,
  on the web and Android), not expired, and its `nonce` claim equal to the
  SHA-256 (hex) of `nonce` (16 to 128 URL-safe characters; required: 400
  without it). The subject is `apple#<sub>`; the email is kept like
  Google's (only when verified; maybe an Apple relay address). `name`
  (Apple gives it to the app only at the first sign-in; whitespace
  collapsed, at most 60 characters) starts the profile, like Google's
  `name` claim. With `authorizationCode` and a Sign in with Apple key
  configured, the function trades the code for a refresh token and keeps
  it with the client it belongs to (item `SUB#apple#<sub>` / `APPLE`) to revoke it when the account is
  deleted ([sign-in.md](sign-in.md#apple-token-revocation)); best effort,
  it never fails the sign-in. 401 `{"error": "invalid Apple ID token"}`
  for a bad, expired, foreign or replayed token.
- **`POST /api/apple/callback`** (public): Sign in with Apple's return
  URL, where Apple's web flow posts its answer on Android
  (`application/x-www-form-urlencoded`: `code`, `id_token`, `state`,
  `user`, or `error`; anything but a form is 415). Answers **307** to
  `intent://callback?<those fields>#Intent;package=com.nu01.grigri;scheme=signinwithapple;end`,
  which opens the Android app; other fields are dropped, and no field
  picks the app. Never logged ([sign-in.md](sign-in.md#apple)).
- The token: 32 random bytes, base64url (43 characters). Stored only as
  its SHA-256 hash: item `SESSION#<hash>` with the subject, the email (only
  if verified), `emailVerified`, the account's name (when given), `createdAt`, `lastUsedAt` and `ttl`
  (DynamoDB's TTL attribute, epoch seconds) = lastUsedAt + **365 days**.
- It slides: a request more than a day after `lastUsedAt` moves both
  forward (at most one write per session per day). No absolute limit: a
  session lasts until sign-out, or 365 days without use. The function
  checks `ttl` itself, since DynamoDB deletes expired items only within a
  few days.
- Every other route but `GET /api/health` takes
  `Authorization: Bearer <session token>`; missing, malformed, unknown or
  expired → 401 `{"error": "signed out"}`.
- `DELETE /api/session`: sign out (this session ends). → `{}`
- `DELETE /api/sessions`: sign out everywhere (every session of my
  account ends; sessions are indexed by subject, `gsi3`). → `{}`
- `DELETE /api/me` (`{"confirm": true}`) deletes the account and ends
  every session of it too ([Routes](#routes)).
- The app: after Google sign-in (any platform) or Sign in with Apple
  (iOS), POST the token to `/api/session`, keep the session token
  (Android/iOS: secure storage, Keychain/Keystore; web: browser storage),
  send it on every call, and never ask Google or Apple again until a 401
  or sign-out. Sign out:
  `DELETE /api/session`, forget the token, sign out of Google in the app.
  A 401 → back to the sign-in screen.

## JSON shapes

Dates are ISO 8601 UTC strings. Photos are S3 keys; the app loads them from
`<site origin>/photos/<key>`.

- **Climber** (profile; `"demo"?: true` when made up, like a Plan's):
  `{"id", "name", "age"?: int, "bio", "photo"?: key, "levels": {"sport": {"scale": "routes", "min": 6, "max": 11}, ...}, "gear": ["rope", ...], "gearPhotos": [key, ...], "location"?: Location, "areas": [Location, ...]}`
  `location` (where I am) and `areas` (up to 5 other places I'd climb
  near) are **private**: only my own profile (`GET`/`PUT /api/me`)
  carries them; everyone else's, in any response's `climbers`, has
  neither. They're stored rounded to 2 decimals (about 1 km), so they
  never say exactly where someone lives.
  Disciplines: sport, trad, bouldering, gym. Scales: `routes` (25 grades,
  indices 0..24; written French 4a..9a or YDS 5.5..5.14d, a display choice
  kept on the device) and `boulders` (15 grades, indices 0..14; Font 3..8B
  or V VB..V13); bouldering uses boulders, the rest routes. Accept the old
  names `french` (= routes) and `vScale` (= boulders) on input; always
  store and return the new names. Gear: rope, quickdraws, rack,
  crashPad, car.
- **Location**: `{"name", "lat", "lon"}`: a named point (a crag, gym
  or town), name 1–120 characters, lat −90..90, lon −180..180.
- **Plan**: `{"id", "organizerId", "discipline", "place", "area", "sectorId"?, "lat"?, "lon"?, "start"?, "end"?, "moreDays"?: [{"start", "end"}], "grades": {"scale","min","max"}, "type"?: "open" | "guided", "price"?: {"amount", "currency"}, "memberIds": [organizer first, then in join order], "notes", "demo"?: true}`. `type`: who lets people in ([plan types](matching.md#plan-types-who-decides)); absent is private (the input takes `"private"` too, and stores it as absent). `price`: a guided plan's, per climber; only guided plans have one. `demo`: made up (the seed's), see [backend](backend.md#the-seed); only the seed sets it (the API's input ignores it).
  No title (the app names a plan by its place), no length in hours (start
  and end), and **no group size: a group is as big as the people who match,
  so nothing is ever "full"**. A plan's days: the first (`start`–`end`), then `moreDays`, soonest first (absent for one day); an undated plan has neither, is never "started" (it can be joined and nudged), and sorts after every dated one. `place` is a sector, crag or gym; `area` is
  where it is ("Siurana, Spain"); `sectorId` is the app's sector-index id
  (e.g. "osm:n123456"), absent for a place typed by hand. `lat` and
  `lon` are where the place is, from the sector index (both or neither,
  kept to 4 decimals); absent for a place typed by hand.
- **JoinRequest**: `{"id": "<planId>/<climberId>", "planId", "climberId", "acceptedBy": [climberIds], "rejected": bool, "time", "nudgedAt"?}`
  (`nudgedAt`: when the requester last [nudged](#routes) the group; absent until they do.)
- **Notice**: `{"id", "kind": "accepted"|"declined"|"request"|"nudge"|"report", "planId", "planTitle" (the plan's place when the notice was made), "climberId"? (who asked, for request and nudge), "time", "read": bool}`.
  `report` goes to admins only, id `reports`, with `planId` and
  `planTitle` empty: there are reports to review.
- **Report** (admins only): `{"id", "kind": "profile"|"plan"|"message"|"pic"|"ad", "targetId", "planId"? (a message's or photo's), "subjectId" (whose content it is), "reporterId", "reason": "spam"|"harassment"|"inappropriate"|"fake"|"other", "text", "content": {"title"?, "text"?, "media"?: [{"key", "kind": "image"|"video"}], "link"?} (a copy, as it was when reported), "status": "open"|"dismissed"|"removed"|"blocked", "time", "resolvedAt"?, "resolvedBy"?}`.
  Apps skip kinds they don't know, so a new kind never breaks an older app.
- **Message**: `{"id", "planId", "authorId": climberId|null, "text", "time", "requestId"?, "attachment"?: {"key", "kind": "image"|"video"}}`
  (authorId null: the chat's own notes: someone joined, left, asked to join;
  a request note carries requestId so the chat shows it as a card. A
  member's message has text, an attachment, or both; `text` is `""` for an
  attachment alone. The attachment is served at `/photos/<key>`.)
- **PlanPic** (a photo of a plan's Your Pics): `{"id", "planId", "key", "uploaderId", "time", "fromChat": bool}`.
  Served at `/photos/<key>`: `plans/<planId>/<random>.<ext>`, or a chat
  photo's `chat/<planId>/...` (`fromChat`).
- **GrigriPic** (a GriGri Pics photo): `{"key", "width", "height", "caption", "author", "license", "licenseUrl", "source", "cragId", "crag"}`.
  Served at `/pics/<key>`; `crag` is the crag's (or area's) name.
- **Wall** (the route finder's): `{"id", "name", "cragId"?, "lat", "lon", "views": [{"key", "width", "height", "h": [9], "addedBy", "time"}], "routes": [Route], "createdBy", "createdAt"}`.
  The first view is the one routes are drawn on (`h` the identity); every
  `h` takes its view's pixels to the first view's.
- **Route**: `{"id", "name", "grade": {"scale", "grade"}, "bolts": [[x, y], ...], "addedBy", "time"}`.
- **Match**: `{"plan": Plan, "newcomerId"}`
- Responses that list plans, requests, notices or messages also return
  `"climbers": {id: Climber}` for every climber they mention, so the app
  never makes one call per person.

## Errors

`{"error": "<message>"}` with 400 (invalid input; `objectionable: <field> …`
when the [filter](moderation.md#the-filter) refuses a name, bio, plan
text, message or ad), 401 (`signed out`: no,
unknown or expired session token; or a bad Google or Apple ID token at
`POST /api/session`),
403 (not allowed; `use the site` for a request that didn't come through
the site's CloudFront, [origin check](origin-check.md)), 404 (no such thing or route), 409 (conflict: already
asked, already a member, changed meanwhile), 413 (body over 64 KB), 415
(a body that isn't `application/json`), 429 (too soon: a nudge within 12
hours of the last), 503 (Premium through Stripe without Stripe keys), 500 (`{"error": "internal error"}`;
details only in the function's log). A signed-in caller without a profile
yet (before their first `GET /api/me`) gets 409 `{"error": "no profile"}`
from every route except `GET/PUT /api/me`, `POST /api/photos`, the
session routes and `GET /api/health`.

## Routes

All need a session token except `GET /api/health`, `POST /api/session`,
`POST /api/stripe/webhook` (signed by Stripe instead) and
`POST /api/apple/notifications` (signed by Apple instead).

|---|---|
| `GET /api/health` | `{"ok": true, "stage": "prod"|"rc"|"local", "version"}` (no auth) |
| `POST /api/session` | body `{"idToken"}`, or `{"appleIdToken", "nonce", "authorizationCode"?, "name"?}` (dev mode: or `{"devUser"}`) → `{"token", "expiresAt"}` (no auth; see [Sessions](#sessions)) |
| `DELETE /api/session` | sign out: this session ends. → `{}` |
| `DELETE /api/sessions` | sign out everywhere: all my sessions end. → `{}` |
| `GET /api/me` | `{"climber": Climber, "admin": bool, "roles": [string] \| null, "premium": {"active", "plan"?, "until"?, "ending"?, "source"?}}` (`premium`: my [Premium](premium.md); `source`, `stripe` or `apple`, says where it's managed). `roles`: my roles in Grigri from rbacr (see **Roles** above), or null when it can't say. The first time, it creates my profile from my account: the session's name (Google's, or the one Apple gave the app at the first sign-in; `Climber` when the session has none), no age, photo, bio, grades, gear or places. Two first calls at once make one profile. |
| `GET /api/realtime` | where [live updates](#live-updates) come from: `{"url": "wss://<IoT endpoint>/mqtt", "authorizer": "<prefix>-api-realtime" (empty locally), "topic": "grigri/<stage>/climbers/<my climber id>/#", "clientIdPrefix": "<my climber id>-"}`, or `{"url": null}` when they're off |
| `DELETE /api/me` | body `{"confirm": true}` (400 without it): deletes my account for good ([sign-in.md](sign-in.md#deleting-my-account)): Premium cancelled at Stripe at once and its rbacr role revoked, then `Deps.onDeleteAccount` (Sign in with Apple's token revocation), then my messages, their media, my request notes and my Your Pics photos in every plan I'm in, left or asked to join; I leave every plan (handed over, or ended with me as its last member; the note says "A climber left the plan"); my requests withdrawn; my ads, profile and gear photos and every item keyed to me deleted; then the sign-in link and every session (later calls: 401). A session route: blocked climbers may call it. Each step can run again: a retry after a failure (Stripe, rbacr, S3) finishes the job. → `{}` |
| `PUT /api/me` | create or update my profile; body: Climber without id. Validates: name 1–60 chars (name and bio through the [filter](moderation.md#the-filter)), age null or 16–99, bio ≤ 1000, valid levels, gear from the list, ≤ 6 gearPhotos, photo keys must be mine (`<climberId or subject hash>/...` as issued by `/api/photos`), location null or a Location, ≤ 5 areas. Photos new to the profile lose their pending tag first (400 if one isn't uploaded, or already expired); photos it no longer uses are deleted. → `{"climber"}` (mine, with location and areas) |
| `GET /api/discover` | plans to swipe on: upcoming (start > now, or undated), I'm not in, I haven't passed or asked, with nobody in the group [blocked](moderation.md#blocking-someone) either way between us; ranked by [how well they match me and how close they are](#the-decks-ranking), best first. → `{"plans": [Plan], "distanceKm": {planId: km}, "climbers"}` (organizers and members; `distanceKm`, whole km from my nearest location or area, only for plans whose distance is known); `"covers": {planId: {"key", "crag", "author", "license"}}`, each plan's best [GriGri Pics](pics.md#on-the-deck) photo (only for plans that have one; from the catalog the function keeps, never failing the deck); for admins also `"scores": {planId: {"score", "level", "reason"}}`, the best 30 plans' [match scores](match-scores.md#on-an-admins-deck); `"ads": [Ad]` and `"adEvery": n`, the [ads](ads.md#on-the-deck) to show between plans (their owners in `climbers`; never failing the deck) |
| `POST /api/plans` | new plan, I organize it; body: Plan without id, organizerId, memberIds. Validates: place required (≤ 80), area ≤ 120, sectorId ≤ 64 when given, start and end both or neither (neither: an **undated** plan, its day still to be decided), start in the future and at most a year away, end after start and at most 24 h later; `moreDays` (only with a start, at most 13: two weeks in all) are more days, each a start–end checked the same way and starting after the day before ends; notes ≤ 1000 (and the place and area when typed by hand) through the [filter](moderation.md#the-filter), grades on the discipline's scale; `type` private (default), open or guided; a guided plan needs `price` (amount > 0 and ≤ 10000 with at most two decimals, currency EUR, USD, GBP, CHF or BRL), which other types drop. → `{"plan"}` |
| `GET /api/plans` | mine: `{"plans": [plans I'm in, soonest first], "asked": [{"request", "plan"}] (my requests still waiting, or declined and not dismissed), "climbers"}` |
| `GET /api/plans/{id}` | `{"plan", "requests": [open requests, only if I'm a member], "climbers"}` |
| `PUT /api/plans/{id}` | organizer only; same body and rules as POST (the whole plan: a `sectorId`, `type` or `price` left out is cleared). A new type that needs fewer yeses lets in whoever now has them (an open plan: everyone waiting). → `{"plan"}` |
| `POST /api/plans/{id}/leave` | I leave (the app's "Cancel the plan"). Organizer leaves → a remaining member picked at random organizes. Last member leaves → the plan, its requests and its chat are gone. Open requests stop waiting for me (so one may now have every yes, and join). A "left" note in the chat. The plan stays out of my deck. → `{}` |
| `POST /api/plans/{id}/join` | swipe right: a join request. Notifies the plan's deciders (every member, or a guided plan's organizer; Notice kind request) and posts a request note in the chat. On an **open** plan nobody decides: no notices or note, and I join at once (membership, the joined note, the accepted notice). 409 if I'm a member, already asked (whatever became of that request), the plan has started, or 30 requests are already waiting on it; "you can't ask to join this plan" when someone in the group blocked me or I blocked them (it doesn't say which). On a **demo** plan, whose made-up members can't answer, the group then says yes at once (as an admin's yes): I join, get the accepted notice, and the chat gets the joined note; the request comes back accepted by every member. → `{"request"}` |
| `POST /api/plans/{id}/nudge` | the requester reminds the group: a Notice kind nudge (`climberId`: me) for each member who hasn't said yes to my open request on the plan. 404 if I haven't asked; 409 if it was declined, I'm already in, or the plan has started; **429** "you nudged the group less than 12 hours ago; try again later" within 12 hours of my last nudge (saved on the request as `nudgedAt`, with a conditional write, so two at once can't both pass). → `{"request"` (with its new `nudgedAt`)`, "nudged": <how many members>}` |
| `POST /api/plans/{id}/pass` | swipe left: out of my deck. → `{}` |
| `DELETE /api/passes` | Discover's refresh: forgets my passes, so those plans are on my deck again; not on plans I asked to join (a declined request I dismissed stays hidden) or left (cancelled: leaving marks its pass `left`). → `{}` |
| `GET /api/requests` | to review: open requests (not rejected) on plans I decide on (I'm in a private plan, or I organize a guided one) that I haven't accepted. → `{"requests", "plans": {id: Plan}, "climbers"}` |
| `POST /api/requests/{planId}/{climberId}/accept` | deciders only (members of a private plan, the organizer of a guided one; 403 otherwise, and on an open plan), or an admin. When every decider has accepted, they join: membership, a "joined" note, a Notice accepted for them; the requests still open on that plan now also wait for the newcomer. → `{"match": Match or null}` |
| `POST /api/requests/{planId}/{climberId}/reject` | deciders only, as for accept, or an admin. One no is enough: rejected, Notice declined for them. → `{}` |
| `POST /api/requests/{planId}/{climberId}/dismiss` | the requester clears a declined request from their plans (the plan stays out of their deck). → `{}` |
| `GET /api/notices` | mine, newest first: `{"notices", "climbers"}` |
| `POST /api/notices/read` | marks all mine read. → `{}` |
| `GET /api/plans/{id}/messages?after=<time>` | members only, oldest first, those after `after` when given. → `{"messages", "climbers"}` |

## The deck's ranking

Each plan scores **fit + 2 × nearness**, each 0 to 1 (pure functions in
[rules.ts](../grigri_api/src/domain/rules.ts)): distance weighs strongly,
twice as much as fit (`NEAR_WEIGHT`). Higher first, then soonest:

- **Fit** (my profile against the plan): 1 when my grades for its
  discipline overlap its grades; 0.6 when one grade apart, then less,
  down to 0 at 4 grades apart; 0 when I don't climb its discipline.
- **Nearness**: e^(−km / 50) for the distance (great circle) from the
  plan's point to the nearest of my location and areas: 1 on my
  doorstep, 0.37 at 50 km, 0.14 at 100 km. 0.25 (like about 70 km
  away) when it isn't known: the plan has no point (typed by hand) or
  I set no location or area.

So a plan in my grades nearby comes first (3), then one nearby a grade
off (2.6), and even one next door that I don't climb (2) comes before one
in my grades 50 km away (1.7) or 150 km away (1.1).

## Live updates

Details: [live-updates.md](live-updates.md).

- **Topics**: `grigri/<stage>/climbers/<climberId>/hint`, one per
  climber; the app subscribes to `grigri/<stage>/climbers/<me>/#`.
- **Connecting**: `<url>?x-amz-customauthorizer-name=<authorizer>&token=<session token>`
  (MQTT 3.1.1 over WebSocket, subprotocol `mqtt`), client id
  `<clientIdPrefix>…`. The authorizer accepts a live session of an
  account with a profile and allows only connecting with that prefix and
  subscribing to and receiving that climber's own topics; anything else
  is refused. Locally (Floci) there's no authorizer.
- **Hints** (QoS 0, JSON): `{"kind": "message"|"request"|"notice"|"plan"|"match"|"pics", "planId"?}`.
  Never data: the app refetches through the routes above.

| Change | Hint, to whom (never the one who made it) |
|---|---|
| `POST /api/plans/{id}/messages` | `message` to the members |
| `POST /api/plans/{id}/join` | `request` to the members |
| accept, not everyone yet | `request` to the members |
| accept, everyone said yes | `match` to the newcomer, `plan` to the other members |
| reject | `notice` to the requester, `request` to the members |
| `POST /api/plans/{id}/nudge` | `notice` to the members who haven't said yes |
| `PUT /api/plans/{id}`, `POST /api/plans/{id}/leave` | `plan` to the (remaining) members |
| `POST /api/reports` | `notice` (no plan) to every admin |
| `POST /api/blocks/{id}` declining their requests | as reject |
| `POST /api/admin/reports/{id}/remove` | `message`, `pics` or `plan` to the plan's members, for removed chat messages, photos or notes |
| `POST /api/plans/{id}/pics`, `DELETE /api/plans/{id}/pics/{picId}` | `pics` to the members |

Publishing is best effort: it waits at most 1.5 s and never fails the
request.

## Seed (RC and local only)

Made-up climbers (never real people) and their plans, dates relative to
now so plans are always upcoming, a few open requests between made-up
climbers so Requests has something. The made-up
climbers have no Google subject (nobody signs in as them) and ids prefixed
`seed-`. The seed is idempotent (re-running refreshes the seed records and
their dates, never touches real people's data) and refuses to run against
prod. Seed plans carry their places' approximate points, so a tester
with a location sees the deck ranked by distance. RC: run after each RC deploy. Local: run when Floci starts.

The seed lives in [grigri_api/seed/](../grigri_api/seed) and runs inside
the stage's function (a direct invoke of `{"grigriSeed": true}`, which the
HTTP API can't send), through [scripts/seed.sh](../scripts/seed.sh).

## Notes on behavior

- Every change to a plan's members or requests is one DynamoDB
  transaction conditioned on the plan's version; a lost race is retried
  (up to 4 times), then answered 409 "changed meanwhile; try again". A
  double join is refused by a conditional put.
- Notices are written after the change commits (best effort, idempotent:
  a notice's id is `<planId>/request/<climberId>`,
  `<planId>/nudge/<climberId>` or `<planId>/accepted|declined`, so a
  repeat replaces it: a new nudge overwrites the last one, unread again).
- When a newcomer joins, they get a request notice for each request still
  waiting on the plan, dated when that person asked.
- The chat's notes: "<name> created the plan. People who match will show
  up here.", "<name> asked to join" (with `requestId`), "<name> joined the
  plan 🎉", "<name> left the plan", and, when the organizer leaves, "<name>
  left the plan; <name> organizes it now".
- Unknown fields in bodies are ignored, never stored. Text is trimmed;
  control characters other than newlines and tabs are refused.
