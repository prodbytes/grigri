# API

The contract between the backend ([grigri_api/](../grigri_api)) and the
app. Architecture, data model and environments: [backend.md](backend.md).

All data comes from the backend. GA (prod) starts EMPTY: only real people's
data. RC and local get made-up data from a seed (never in GA). There are no
auto-answering fake climbers anywhere: every environment behaves like GA.
An admin can approve or reject any join request.

## Architecture (cost first: $0 idle)

- One TypeScript Lambda (Node.js 22, arm64, 256 MB) with an internal router,
  behind one API Gateway **HTTP API** ($1/M requests), served under `/api/*`
  by the site's existing CloudFront distribution (same origin as the web
  app, so no CORS in prod).
- One DynamoDB table, on-demand (PAY_PER_REQUEST), single-table design,
  point-in-time recovery on in prod only.
- Photos in S3 (private), uploaded with presigned POSTs, served by the same
  CloudFront under `/photos/*` (origin access control). Never in DynamoDB
  (400 KB item limit).
- Auth: the API's own **sessions** (see [Sessions](#sessions)). The app
  trades a Google ID token for a session token once (`POST /api/session`,
  where the function verifies the token), then sends
  `Authorization: Bearer <session token>` on every call. A session lasts
  until sign-out, or 365 days without use. The HTTP API has no
  authorizer: the function authenticates every request (one DynamoDB
  read).
- Live updates: after a change the function publishes a hint to each
  affected climber's MQTT topic on AWS IoT Core; the app subscribes with
  its session token through an IoT custom authorizer (see
  [Live updates](#live-updates) and [live-updates.md](live-updates.md)).
- Stacks per stage: `<prefix>-api` (prefix `grigri` for prod, `grigri-rc`
  for RC), next to the existing `<prefix>-web`.
- Local: the same CloudFormation template (`grigri_api/template.yaml`) deployed into Floci (Lambda, HTTP API,
  DynamoDB, S3), like prodbytes/presence's `presence_floci/init/ready.d/05-auth-api.sh`,
  and Floci's CloudFront routes `/api/*` and `/photos/*` to it.
- **Dev mode, local only**: when no Google web client ID is configured
  locally, the API takes the caller from an `X-Grigri-Dev-User: <email>`
  header, and `POST /api/session` also takes `{"devUser": "<email>"}`
  (a real session for `dev#<email>`). The template must refuse dev mode
  unless the stage is `local` (a CloudFormation Rule), so it can never be
  deployed to RC or GA; the function also ignores the header and refuses
  `devUser` unless its stage is `local`.

## Identity

- A signed-in Google account is a **subject** `https://accounts.google.com#<sub>`
  (whichever issuer spelling the token had; `dev#<email>` in dev mode), linked to one
  **climber id** (random, URL-safe, generated by the server at the first
  profile save). Emails are never returned to other people.
- **Admin**: decided by [rbacr](roles.md) on every request: the
  session's verified email (`email_verified` true when the session was
  made) holds the `admin` role of rbacr's `grigri` system (rbacr's roots
  hold every role, so they're admins too). The API asks
  `POST <RbacrUrl>/api/check` `{email, systemId: "grigri", role: "admin"}`
  with an rbacr root's API token (template parameter `RbacrToken`, from
  the repository secret `GRIGRI_RBACR_TOKEN`), with a 2 s timeout, and
  keeps each answer for 60 s per Lambda instance, so a granted or revoked
  role shows within a minute. It fails closed: no token, an error or a
  timeout means not an admin (and isn't kept); rbacr not knowing the
  `grigri` system or its `admin` role means nobody is. Both stages ask
  production's rbacr (https://rbacr.nu01.com). Locally the API asks the
  local rbacr with `.env`'s `RBACR_TOKEN`, and in dev mode the header's
  (or `devUser`'s) email counts as verified.

## Sessions

Google ID tokens expire after an hour and can't be refreshed quietly on
the web, so the API issues its own sessions:

- `POST /api/session` (public; the only route that takes a Google ID
  token), body `{"idToken": "<Google ID token>"}`. The function verifies
  it: RS256 signature against Google's keys
  (`https://www.googleapis.com/oauth2/v3/certs`, cached across warm
  invocations), `iss` `accounts.google.com` or
  `https://accounts.google.com`, `aud` the Google **web** client ID or
  one of the stage's **iOS** client IDs (template parameter
  `GoogleIosClientIds`: production's `GOOGLE_IOS_CLIENT_ID`; the RC's
  `GOOGLE_IOS_CLIENT_ID_RC` and production's, while phone builds for the
  RC keep production's bundle ID), not expired; with no web client
  configured, none. It keeps the token's `name` claim (whitespace collapsed, at
  most 60 characters) for the profile `GET /api/me` creates; dev mode
  uses the email's part before the @. → `{"token": "<opaque>", "expiresAt": "<ISO time>"}`. 401
  `{"error": "invalid Google ID token"}` for a bad, expired or foreign
  token; 400 without `idToken`. Dev mode only: `{"devUser": "<email>"}`
  instead (401 outside dev mode).
- The token: 32 random bytes, base64url (43 characters). Stored only as
  its SHA-256 hash: item `SESSION#<hash>` with the subject, the email (only
  if verified), `emailVerified`, the Google name (when given), `createdAt`, `lastUsedAt` and `ttl`
  (DynamoDB's TTL attribute, epoch seconds) = lastUsedAt + **365 days**.
- It slides: a request more than a day after `lastUsedAt` moves both
  forward (at most one write per session per day). No absolute limit: a
  session lasts until sign-out, or 365 days without use. The function
  checks `ttl` itself, since DynamoDB deletes expired items only within a
  few days.
- Every other route but `GET /api/health` takes
  `Authorization: Bearer <session token>`; missing, malformed, unknown or
  expired → 401 `{"error": "signed out"}`.
- `DELETE /api/session`: sign out (this session ends). → `{}`
- `DELETE /api/sessions`: sign out everywhere (every session of my
  account ends; sessions are indexed by subject, `gsi3`). → `{}`
- The app: after Google sign-in (any platform), POST the ID token to
  `/api/session`, keep the session token (Android/iOS: secure storage,
  Keychain/Keystore; web: browser storage), send it on every call, and
  never ask Google again until a 401 or sign-out. Sign out:
  `DELETE /api/session`, forget the token, sign out of Google in the app.
  A 401 → back to the sign-in screen.

## JSON shapes

Dates are ISO 8601 UTC strings. Photos are S3 keys; the app loads them from
`<site origin>/photos/<key>`.

- **Climber** (profile):
  `{"id", "name", "age"?: int, "bio", "photo"?: key, "levels": {"sport": {"scale": "routes", "min": 6, "max": 11}, ...}, "gear": ["rope", ...], "gearPhotos": [key, ...], "location"?: Location, "areas": [Location, ...]}`
  `location` (where I am) and `areas` (up to 5 other places I'd climb
  near) are **private**: only my own profile (`GET`/`PUT /api/me`)
  carries them; everyone else's, in any response's `climbers`, has
  neither. They're stored rounded to 2 decimals (about 1 km), so they
  never say exactly where someone lives.
  Disciplines: sport, trad, bouldering, gym. Scales: `routes` (25 grades,
  indices 0..24; written French 4a..9a or YDS 5.5..5.14d, a display choice
  kept on the device) and `boulders` (15 grades, indices 0..14; Font 3..8B
  or V VB..V13); bouldering uses boulders, the rest routes. Accept the old
  names `french` (= routes) and `vScale` (= boulders) on input; always
  store and return the new names. Gear: rope, quickdraws, rack,
  crashPad, car.
- **Location**: `{"name", "lat", "lon"}`: a named point (a crag, gym
  or town), name 1–120 characters, lat −90..90, lon −180..180.
- **Plan**: `{"id", "organizerId", "discipline", "place", "area", "sectorId"?, "lat"?, "lon"?, "start", "end", "grades": {"scale","min","max"}, "memberIds": [organizer first, then in join order], "notes"}`.
  No title (the app names a plan by its place), no length in hours (start
  and end), and **no group size: a group is as big as the people who match,
  so nothing is ever "full"**. `place` is a sector, crag or gym; `area` is
  where it is ("Siurana, Spain"); `sectorId` is the app's sector-index id
  (e.g. "osm:n123456"), absent for a place typed by hand. `lat` and
  `lon` are where the place is, from the sector index (both or neither,
  kept to 4 decimals); absent for a place typed by hand.
- **JoinRequest**: `{"id": "<planId>/<climberId>", "planId", "climberId", "acceptedBy": [climberIds], "rejected": bool, "time"}`
- **Notice**: `{"id", "kind": "accepted"|"declined"|"request", "planId", "planTitle" (the plan's place when the notice was made), "climberId"?, "time", "read": bool}`
- **Message**: `{"id", "planId", "authorId": climberId|null, "text", "time", "requestId"?}`
  (authorId null: the chat's own notes: someone joined, left, asked to join;
  a request note carries requestId so the chat shows it as a card.)
- **Match**: `{"plan": Plan, "newcomerId"}`
- Responses that list plans, requests, notices or messages also return
  `"climbers": {id: Climber}` for every climber they mention, so the app
  never makes one call per person.

## Errors

`{"error": "<message>"}` with 400 (invalid input), 401 (`signed out`: no,
unknown or expired session token; or a bad Google ID token at
`POST /api/session`),
403 (not allowed), 404 (no such thing or route), 409 (conflict: already
asked, already a member, changed meanwhile), 413 (body over 64 KB), 415
(a body that isn't `application/json`), 500 (`{"error": "internal error"}`;
details only in the function's log). A signed-in caller without a profile
yet (before their first `GET /api/me`) gets 409 `{"error": "no profile"}`
from every route except `GET/PUT /api/me`, `POST /api/photos`, the
session routes and `GET /api/health`.

## Routes

All need a session token except `GET /api/health` and `POST /api/session`.

| Route | Does |
|---|---|
| `GET /api/health` | `{"ok": true, "stage": "prod"|"rc"|"local", "version"}` (no auth) |
| `POST /api/session` | body `{"idToken"}` (dev mode: or `{"devUser"}`) → `{"token", "expiresAt"}` (no auth; see [Sessions](#sessions)) |
| `DELETE /api/session` | sign out: this session ends. → `{}` |
| `DELETE /api/sessions` | sign out everywhere: all my sessions end. → `{}` |
| `GET /api/me` | `{"climber": Climber, "admin": bool}`. The first time, it creates my profile from my Google account: the session's name (`Climber` when the session has none, as sessions from before names were kept), no age, photo, bio, grades, gear or places. Two first calls at once make one profile. |
| `GET /api/realtime` | where [live updates](#live-updates) come from: `{"url": "wss://<IoT endpoint>/mqtt", "authorizer": "<prefix>-api-realtime" (empty locally), "topic": "grigri/<stage>/climbers/<my climber id>/#", "clientIdPrefix": "<my climber id>-"}`, or `{"url": null}` when they're off |
| `PUT /api/me` | create or update my profile; body: Climber without id. Validates: name 1–60 chars, age null or 16–99, bio ≤ 1000, valid levels, gear from the list, ≤ 6 gearPhotos, photo keys must be mine (`<climberId or subject hash>/...` as issued by `/api/photos`), location null or a Location, ≤ 5 areas. Photos new to the profile lose their pending tag first (400 if one isn't uploaded, or already expired); photos it no longer uses are deleted. → `{"climber"}` (mine, with location and areas) |
| `GET /api/discover` | plans to swipe on: upcoming (start > now), I'm not in, I haven't passed or asked; ranked by [how well they match me and how close they are](#the-decks-ranking), best first. → `{"plans": [Plan], "distanceKm": {planId: km}, "climbers"}` (organizers and members; `distanceKm`, whole km from my nearest location or area, only for plans whose distance is known) |
| `POST /api/plans` | new plan, I organize it; body: Plan without id, organizerId, memberIds. Validates: place required (≤ 80), area ≤ 120, sectorId ≤ 64 when given, start in the future, end after start and at most 24 h later, notes ≤ 1000, grades on the discipline's scale. → `{"plan"}` |
| `GET /api/plans` | mine: `{"plans": [plans I'm in, soonest first], "asked": [{"request", "plan"}] (my requests still waiting, or declined and not dismissed), "climbers"}` |
| `GET /api/plans/{id}` | `{"plan", "requests": [open requests, only if I'm a member], "climbers"}` |
| `PUT /api/plans/{id}` | organizer only; same body and rules as POST (the whole plan: a `sectorId` left out is cleared). → `{"plan"}` |
| `POST /api/plans/{id}/leave` | I leave. Organizer leaves → next member organizes. Last member leaves → the plan, its requests and its chat are gone. Open requests stop waiting for me (so one may now have every yes, and join). A "left" note in the chat. The plan stays out of my deck. → `{}` |
| `POST /api/plans/{id}/join` | swipe right: a join request. Notifies every member (Notice kind request) and posts a request note in the chat. 409 if I'm a member, already asked (whatever became of that request), the plan has started, or 30 requests are already waiting on it. → `{"request"}` |
| `POST /api/plans/{id}/pass` | swipe left: out of my deck. → `{}` |
| `GET /api/requests` | to review: open requests (not rejected) on plans I'm in that I haven't accepted. → `{"requests", "plans": {id: Plan}, "climbers"}` |
| `POST /api/requests/{planId}/{climberId}/accept` | member only. When every current member has accepted, they join: membership, a "joined" note, a Notice accepted for them; the requests still open on that plan now also wait for the newcomer. → `{"match": Match or null}` |
| `POST /api/requests/{planId}/{climberId}/reject` | member only. One no is enough: rejected, Notice declined for them. → `{}` |
| `POST /api/requests/{planId}/{climberId}/dismiss` | the requester clears a declined request from their plans (the plan stays out of their deck). → `{}` |
| `GET /api/notices` | mine, newest first: `{"notices", "climbers"}` |
| `POST /api/notices/read` | marks all mine read. → `{}` |
| `GET /api/plans/{id}/messages?after=<time>` | members only, oldest first, those after `after` when given. → `{"messages", "climbers"}` |
| `POST /api/plans/{id}/messages` | members only; body `{"text"}` 1–2000 chars. → `{"message"}` |
| `POST /api/photos` | body `{"kind": "profile"|"gear", "contentType": "image/jpeg"|"image/png"|"image/webp"}` → `{"key", "url", "fields"}`: a presigned S3 POST, ≤ 2 MB, valid 5 minutes. The app POSTs the file there (multipart form with every returned field, then the file, as the last field named `file`; no Authorization header) and saves the key in its profile. The fields include `tagging` (`grigri-pending=true`): the bucket expires pending photos after a day, so a photo never saved to a profile goes away. Keys are `<subject hash>/<kind>/<random>.<jpg|png|webp>`; the S3 object is `photos/<key>`, served at `/photos/<key>`. In AWS `url` is the bucket's own (`https://<bucket>.s3.us-east-1.amazonaws.com/`, allowed by the web app's CSP `connect-src` and the bucket's CORS for the stage's site origin); locally it's Floci's S3, `https://localhost:2543/grigri-local-photos`. |
| `GET /api/admin/requests` | admin only: every open request (not rejected, not joined) → `{"requests", "plans": {id: Plan}, "climbers"}` |
| `POST /api/admin/requests/{planId}/{climberId}/accept` | admin only: they join now, as if every member accepted; same notes and Notice. → `{"match"}` |
| `POST /api/admin/requests/{planId}/{climberId}/reject` | admin only: rejected, Notice declined. → `{}` |

## The deck's ranking

Each plan scores **fit + nearness**, each 0 to 1 (pure functions in
[rules.ts](../grigri_api/src/domain/rules.ts)); higher first, then
soonest:

- **Fit** (my profile against the plan): 1 when my grades for its
  discipline overlap its grades; 0.6 when one grade apart, then less,
  down to 0 at 4 grades apart; 0 when I don't climb its discipline.
- **Nearness**: e^(−km / 50) for the distance (great circle) from the
  plan's point to the nearest of my location and areas: 1 on my
  doorstep, 0.37 at 50 km, 0.14 at 100 km. 0.25 (like about 70 km
  away) when it isn't known: the plan has no point (typed by hand) or
  I set no location or area.

So a plan in my grades nearby comes first, and a plan in my grades
150 km away still comes before one next door that I don't climb.

## Live updates

Details: [live-updates.md](live-updates.md).

- **Topics**: `grigri/<stage>/climbers/<climberId>/hint`, one per
  climber; the app subscribes to `grigri/<stage>/climbers/<me>/#`.
- **Connecting**: `<url>?x-amz-customauthorizer-name=<authorizer>&token=<session token>`
  (MQTT 3.1.1 over WebSocket, subprotocol `mqtt`), client id
  `<clientIdPrefix>…`. The authorizer accepts a live session of an
  account with a profile and allows only connecting with that prefix and
  subscribing to and receiving that climber's own topics; anything else
  is refused. Locally (Floci) there's no authorizer.
- **Hints** (QoS 0, JSON): `{"kind": "message"|"request"|"notice"|"plan"|"match", "planId"?}`.
  Never data: the app refetches through the routes above.

| Change | Hint, to whom (never the one who made it) |
|---|---|
| `POST /api/plans/{id}/messages` | `message` to the members |
| `POST /api/plans/{id}/join` | `request` to the members |
| accept (member or admin), not everyone yet | `request` to the members |
| accept, everyone said yes (or an admin) | `match` to the newcomer, `plan` to the other members |
| reject (member or admin) | `notice` to the requester, `request` to the members |
| `PUT /api/plans/{id}`, `POST /api/plans/{id}/leave` | `plan` to the (remaining) members |

Publishing is best effort: it waits at most 1.5 s and never fails the
request.

## Seed (RC and local only)

Made-up climbers (never real people) and their plans, dates relative to
now so plans are always upcoming, a few open requests between made-up
climbers so the admin view and Requests have something. The made-up
climbers have no Google subject (nobody signs in as them) and ids prefixed
`seed-`. The seed is idempotent (re-running refreshes the seed records and
their dates, never touches real people's data) and refuses to run against
prod. Seed plans carry their places' approximate points, so a tester
with a location sees the deck ranked by distance. RC: run after each RC deploy. Local: run when Floci starts.

The seed lives in [grigri_api/seed/](../grigri_api/seed) and runs inside
the stage's function (a direct invoke of `{"grigriSeed": true}`, which the
HTTP API can't send), through [scripts/seed.sh](../scripts/seed.sh).

## Notes on behavior

- Every change to a plan's members or requests is one DynamoDB
  transaction conditioned on the plan's version; a lost race is retried
  (up to 4 times), then answered 409 "changed meanwhile; try again". A
  double join is refused by a conditional put.
- Notices are written after the change commits (best effort, idempotent:
  a notice's id is `<planId>/request/<climberId>` or
  `<planId>/accepted|declined`, so a repeat replaces it).
- When a newcomer joins, they get a request notice for each request still
  waiting on the plan, dated when that person asked.
- The chat's notes: "<name> created the plan. People who match will show
  up here.", "<name> asked to join" (with `requestId`), "<name> joined the
  plan 🎉", "<name> left the plan".
- Unknown fields in bodies are ignored, never stored. Text is trimmed;
  control characters other than newlines and tabs are refused.
